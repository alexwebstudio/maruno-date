> Статус: **аналитический документ**. Никаких миграций и изменений схемы по нему не выполнено.
> Подготовлен на этапе визуальной переработки Maruno Wedding (версия 1.2) по отдельному запросу.

## 1. Что есть сейчас

### 1.1 Авторизация

- Один Supabase-проект, стандартный `auth.users` (email + пароль).
- Клиентский хелпер `lib/supabase/client.ts` (`createBrowserClient`), серверный — `lib/supabase/server.ts`.
- Состояние сессии — хук `lib/hooks/useAuth.ts` (`getUser()` + `onAuthStateChange`).
- Никаких ролей, организаций, профилей пользователя в БД нет. Профиль = запись в `auth.users`.

### 1.2 Хранение сайтов

Таблица `public.projects`:

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid → `auth.users(id)` | каскадное удаление |
| `title` | text | |
| `slug` | text **UNIQUE** | глобально уникален на всю базу |
| `template` | text, default `classic-luxury` | |
| `language` | text (`ru` / `kz`) | |
| `colors`, `fonts`, `music`, `blocks` | jsonb | всё содержимое сайта живёт здесь |
| `published` | boolean | |
| `notify_email`, `access_secret` | text | добавлены миграцией 1.01 |
| `created_at`, `updated_at` | timestamptz | триггер на `updated_at` |

RLS: владелец видит/меняет своё, все читают `published = true`.

### 1.3 Смежные таблицы

- `public.rsvp_responses` — ответы гостей, привязка к `project_id`.
- `public.user_settings` — `user_id` PK + `settings jsonb` (дефолты сайта, доступ, канал сообщений).
- `public.reviews`, `public.subscribers` — публичные отзывы и подписка на апдейты, к аккаунтам не привязаны.

### 1.4 Тарифы и оплата

Оплаты в БД **нет вообще**. `lib/subscription.ts`:

- план хранится в `localStorage` по ключу `wedify.plan.<user_id>`;
- публичный билд жёстко ограничен планом `standard` (`MAX_PUBLIC_PLAN`);
- список премиум-почт (`PREMIUM_EMAILS`) в публичной сборке пуст;
- лимит сайтов считается на лету в `app/dashboard/new/page.tsx` (`plan === 'premium' ? 3 : plan === 'standard' ? 2 : 1`).

Практический вывод: тариф сейчас не является серверной сущностью и не переживает смену устройства/браузера. Любая реальная монетизация потребует таблицы в БД независимо от мультипродуктовой истории.

## 2. Целевая модель (со слов заказчика)

Одна Supabase, один аккаунт, единый вход между направлениями Maruno (Wedding / Birthday / Gender Reveal / Date / общий кабинет). Сайт принадлежит направлению через поле `category` / `event_type`. Внутри направления пользователь видит только свои сайты этого типа, в общем кабинете — все. Оплаты, тарифы и публикации считаются отдельно по каждому сайту и направлению.

## 3. Насколько текущая структура к этому готова

### Готово без изменений

- **Единая авторизация.** `auth.users` один на проект; несколько фронтендов на разных доменах могут работать с одним Supabase. Ничего переделывать не нужно.
- **Формат контента сайта.** `blocks jsonb` не завязан на свадебную специфику структурно — типы блоков это просто строки. Другое направление сможет добавить свои типы блоков без изменения схемы.
- **RLS-модель.** Политики построены на `auth.uid() = user_id` — они автоматически продолжат работать при добавлении столбца категории.
- **Настройки пользователя.** `user_settings` уже отдельная таблица с jsonb — легко расширить до «настройки на направление».

### Требует доработки

1. **Нет поля категории.** `projects` не различает тип события. Это единственное блокирующее изменение схемы — один nullable-столбец с дефолтом.

2. **`slug` глобально уникален.** Сейчас `UNIQUE` на всю таблицу. При нескольких направлениях `maruno.kz/wedding/anna-i-petr` и `maruno.kz/date/anna-i-petr` конфликтовать не должны, а сейчас конфликтуют. Нужно решить: либо оставить глобальную уникальность (проще, ссылки остаются короткими), либо перейти на составной уникальный ключ `(category, slug)`. Рекомендация — **оставить глобальную**, пока направления живут на разных доменах/поддоменах: это не требует миграции и не ломает существующие ссылки.

3. **Тариф не в БД.** `localStorage` не подходит для «оплаты отдельно по каждому сайту и направлению». Нужна отдельная сущность (см. п. 4.2).

4. **Публикация — просто boolean.** `published` не знает, оплачена публикация или нет, до какого срока и по какому тарифу. Для платной публикации потребуется расширение.

5. **`lib/projects.ts` не фильтрует по типу.** `getProjects(userId)` возвращает всё. Клиентская фильтрация появится вместе со столбцом категории — это правка одной функции, не архитектуры.

6. **Терминология «wedify» в ключах.** `wedify.plan.*`, `wedify:user-settings` — при объединении направлений эти ключи стоит перевести на нейтральный `maruno.*`, иначе на общем домене они начнут пересекаться между продуктами.

**Общий вывод: структура к целевой модели готова на ~80%.** Ядро (единый аккаунт, единая таблица сайтов, RLS по владельцу) уже правильное. Не хватает измерения «направление» и серверного учёта оплат.

## 4. Предложение для следующего этапа

### 4.1 Минимальная миграция — один столбец

```sql
ALTER TABLE public.projects
  ADD COLUMN IF NOT EXISTS event_type TEXT NOT NULL DEFAULT 'wedding';

CREATE INDEX IF NOT EXISTS idx_projects_user_event
  ON public.projects(user_id, event_type, created_at DESC);
```

Свойства:
- обратно совместима — все существующие записи получают `'wedding'`;
- ничего не ломает: старый код, который не знает про столбец, продолжает работать;
- RLS не меняется;
- откат — `DROP COLUMN`.

Значения: `wedding` | `birthday` | `gender_reveal` | `date` | далее по мере запуска направлений. Строка, а не enum — чтобы добавление направления не требовало миграции.

**Реализовано.** В Maruno Date направление зафиксировано константой
`APP_EVENT_TYPE` в `types/index.ts`, а `getProjects()` и `createProject()`
фильтруют и проставляют его. Если миграция ещё не применена, оба метода
откатываются к прежнему поведению и пишут предупреждение в консоль —
кабинет продолжает работать, просто показывает сайты всех направлений.

В коде: `getProjects(userId, eventType)` добавляет `.eq('event_type', eventType)`; каждое приложение-направление передаёт свою константу; общий кабинет Maruno вызывает без фильтра.

### 4.2 Учёт оплат — отдельная таблица

Оплату лучше не класть в `projects` (иначе история платежей затирается при каждой правке сайта):

```sql
CREATE TABLE public.entitlements (
  id          UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  user_id     UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  project_id  UUID REFERENCES public.projects(id) ON DELETE CASCADE, -- NULL = право на уровне аккаунта
  event_type  TEXT NOT NULL,
  plan        TEXT NOT NULL,          -- start | standard | premium
  source      TEXT,                   -- kaspi | robokassa | manual | promo
  valid_until TIMESTAMPTZ,            -- NULL = бессрочно
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

Это закрывает требование «оплаты, тарифы и публикации учитываются отдельно для каждого сайта и направления»: `project_id IS NULL` — право на всё направление, `project_id` заполнен — оплата конкретного сайта.

Важно: запись в `entitlements` должна создаваться **только с сервера** (service role / webhook платёжной системы). RLS: пользователю — только `SELECT` своих строк, без `INSERT`/`UPDATE`.

### 4.3 Порядок внедрения

| Шаг | Содержание | Риск |
|---|---|---|
| 1 | Миграция `event_type` с дефолтом | минимальный, обратимо |
| 2 | `getProjects` / `createProject` учитывают `event_type`; константа направления в конфиге приложения | низкий |
| 3 | Переименование localStorage-ключей `wedify.*` → `maruno.*` с чтением старого ключа как fallback | низкий |
| 4 | Таблица `entitlements` + серверное чтение плана вместо `localStorage` | средний — затрагивает `lib/subscription.ts` и лимиты сайтов |
| 5 | Подключение реальной платёжной системы, webhook пишет `entitlements` | отдельный этап |
| 6 | Общий кабинет Maruno (список всех событий) | отдельный этап |

Шаги 1–3 безопасны и не меняют поведение продукта. Шаг 4 — первый, который меняет бизнес-логику, и его стоит согласовывать отдельно.

### 4.4 Открытые вопросы к заказчику

1. Направления живут на **разных доменах** (`wedding.maruno.kz`) или на **одном с префиксом пути** (`maruno.kz/wedding`)? От этого зависит решение по уникальности `slug` и по способу шаринга сессии.
2. Тариф покупается **на аккаунт**, **на направление** или **на конкретный сайт**? В `Pricing.tsx` сейчас написано «доступ навсегда для этой почты» — то есть на аккаунт; в `dashboard/new` лимит считается по числу сайтов. Это противоречие нужно разрешить до реализации `entitlements`.
3. Что происходит с уже опубликованным сайтом, если срок оплаты истёк — сайт скрывается, показывает заглушку или остаётся доступным?
